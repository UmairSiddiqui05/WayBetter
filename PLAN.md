# Plan: Multimodal Park-and-Ride Trip Planner (NYC Metro)
_Locked via grill — by Claude + Umair. Revised after Codex review round 1._

## Goal

Build and ship a park-and-ride decision engine for the NYC metro area: given an origin, destination, and time, it compares full-drive, full-transit, and drive-to-station hybrid itineraries across real tradeoffs (time, total cost incl. gas/parking/fares/tolls, driving exposure, transfers, walking, parking confidence) and explains its recommendations. It is simultaneously a portfolio piece for full-time CS recruiting and a real shipped product: **web app first** (live URL ≈ Sept 1, 2026 target), **iOS App Store second** (immediately after), Android later. Solo developer using AI agents as the workforce; monetization is explicitly not a goal.

## Approach

1. **Infrastructure baseline.** Single Hetzner CPX41-class VPS (16 GB RAM, ~$30/mo, US-East Ashburn) running Docker Compose: FastAPI backend, PostgreSQL + PostGIS, Redis, OpenTripPlanner 2.x, and a jobs worker. Repo structure per PRD §18 (backend / web / ios / data / docs).
2. **Ops from day one (not later).** OTP graph builds run **off-box** (CI or ephemeral instance) producing versioned graph artifacts; OTP deploys blue/green — new container loads new graph, passes health-check trip queries, then traffic cuts over. Nightly encrypted Postgres backups shipped off-box with a documented restore drill; secrets via environment/secret files never committed; health checks + uptime monitoring; provider-quota and spend alerts for Mapbox/Gemini.
3. **Data ingestion (Phase 0).** Scripted downloads + loaders for GTFS static feeds — launch scope: NJ Transit rail, NJ Transit commuter bus, LIRR, Metro-North (incl. New Haven line), NYC Subway, PATH, CT rail (Shore Line East, Hartford Line). OSM extract for the NY metro region. Fast-follows are **defined work packages, not free**: local buses ≈ feeds + graph rebuild + bus-preference filters and fare entries; GBFS micromobility ≈ feed ingestion + last-mile estimator + operator deep links + API/UI fields (the deferred bike/scooter toggle ships with this package).
4. **Regions are data, not code — with honest agency escape hatches.** A region = config entry: bounding box, GTFS feed registry, OTP graph reference, fare-table files, toll-table files, parking seed file, agency rule modules. Stations get **canonical internal IDs** with a mapping table `(region, feed_id, agency_id, gtfs_stop_id, feed_version)` so feed refreshes and cross-feed collisions can't corrupt identity. Agency-specific behavior (fare quirks, GTFS-RT matching, parking rules) lives in **versioned per-agency data/rule modules**, not inline conditionals — expansion to a new metro = new config + data + rule modules.
5. **Parking database.** Manual-plus-agent-researched seed data for the top ~60–75 park-and-ride stations region-wide (≈30 NJT, ≈15 LIRR, ≈15 MNR, ≈10 CT): lot name, location, daily/hourly price, payment method, permit/overnight restrictions, capacity, source URL, last-verified date, **and source license/permission** — data comes from official agency pages, municipal open data, OSM (ODbL-attributed), or human-entered facts; no scraping of ToS-restricted sources. All other stations appear with honest "parking info unknown" labels. Candidate filtering excludes only **known-unusable** parking (e.g., permit-only with no daily option); unknown-parking stations remain candidates with nullable cost, "unknown" confidence, and a scoring penalty. Human spot-check required — parking-price errors are the credibility killer.
6. **Routing pipeline** (the core engine):
   - Optional LLM constraint extraction (natural-language input → validated Pydantic `TripRequest`; form input skips this).
   - **Canonical time model** (all timestamps timezone-aware; **timezone is a region config field**, NYC = America/New_York): `leave_now`/`leave_at` plan forward. `arrive_by` plans **backward**: OTP computes the transit leg with its native arrive-by search → required station boarding time → subtract a parking-and-walk buffer (per-station, default ~7 min) → required parking arrival. Drive-leg timing per Mapbox capability: **Matrix has no arrive-by** (fine — it only prunes); **Directions `arrive_by` (driving profile, typical/historical traffic) solves finalists directly**, with an optional `driving-traffic` + `depart_at` refinement pass when departure is near-term and live traffic matters. Provider capability differences live behind the `DrivingProvider` interface.
   - Candidate station generator: **drive-time isochrone from origin** (Mapbox Isochrone or OSM-based) intersected with stations ranked by **precomputed station→destination-zone transit travel times** (batch-generated from OTP), with diversity quotas by agency/line so one corridor doesn't monopolize; includes destination-adjacent stations (supports "Most Driving" mode). Pruned to ~20 candidates. The precompute table, OTP graph, feed metadata, and candidate-cache version deploy as **one atomic versioned bundle** (blue/green swaps the whole bundle) so candidate selection can never race a graph cutover.
   - Fan-out driving legs via Mapbox `driving-traffic` **Matrix API chunked at its 10-coordinate limit** (~3 calls for 20 candidates) for candidate pruning; **Directions API on finalists only** (top ~5) for geometry, toll flags, and avoid-toll routing. **When `avoid_tolls` is active, toll-blind Matrix pruning is skipped entirely: `exclude=toll` Directions runs on all ~20 isochrone-selected candidates before any candidate is dropped** (Matrix has no `exclude`, and pruning on toll-allowed durations could discard the candidate that wins toll-free) — ~20 Directions calls only in that mode, still trivially within free tier. Transit legs via self-hosted OTP; plus drive-all-the-way and pure-transit baselines.
   - Cost estimator: gas (vehicle profile MPG × regional gas price), EV variant, parking (seed DB), transit fare (fare tables), and **tolls computed geometrically**: route polylines intersected against **versioned, direction-aware toll-crossing geometries** (GWB, Lincoln, Holland, Verrazzano, etc.) with E-ZPass vs cash rates per vehicle/payment profile, plus NYC congestion-zone entry detection — Directions toll *flags* are advisory only; `exclude=toll` serves avoid-toll routing, never pricing. Also a simple **emissions estimator** (drive miles × vehicle CO₂/mile from profile; transit legs × published per-passenger-mile factors, all as data files) so `emissions_estimate` exists in the model even though the "lowest emissions" sort stays out of the launch UI.
   - Scoring engine: the 17 PRD modes are **explicitly classified into hard filters (avoid tolls, avoid city driving, mode include/exclude), preference weights (driving penalty, cost sensitivity), and deterministic sort keys (fastest, cheapest, least/most driving, fewest transfers, best parking)** — each with unit tests; produces labels, badges, warnings.
   - **"Avoid city driving" is defined, not vibes**: each region config carries `city_driving_zone` polygons (NYC region: Manhattan plus configurable urban cores like downtown Newark/Jersey City). A route violates the filter iff any **driving-leg** polyline intersects a zone polygon (PostGIS intersection test). If the *destination* itself is inside a zone, the filter excludes only options whose drive legs enter it — drive-all-the-way gets filtered out (or shown as an explicitly-labeled "violates your city-driving preference" baseline), while park-and-ride options that keep all driving outside the zone remain; transit/walk legs inside the zone never violate. Behavior unit-tested for the destination-in-zone case.
   - LLM explanation for top 3–5 routes only, generated from computed metrics (template-grounded; LLM smooths wording, cannot introduce data).
7. **Fares.** All fares are **effective-dated data files with source URLs — zero fare literals in code or docs**: zone-pair tables for NJT/LIRR/MNR with peak/off-peak from day one, flat-fare entries for subway and PATH at their current published rates, CT tables. GTFS-fares importer pre-fills where feeds carry usable data; a refresh job flags tables past their verification window. Adult rider profile at launch; profile enum designed so discount tiers are additive data.
8. **Real-time = alerts-informed scoring.** Poll GTFS-RT service alerts per agency; tag affected route options via structured route/stop ID matching; penalize reliability score, show a warning chip, and display the agency's alert text — **sanitized and escaped (never rendered as HTML), truncated in list views with full text in the detail view, source-attributed** ("NEC delays up to 20 min — NJ Transit"). **Scheduled ETAs are never arithmetically adjusted from alert text** — alerts are warnings, not canonical delay data. ETA adjustment and delay-aware rerouting arrive in v1.1 with GTFS-RT TripUpdates → OTP.
9. **AI layer.** `LLMProvider` interface (same pattern as `DrivingProvider`); launch default **Gemini 2.5 Flash-Lite**; swapping models = config + one adapter. Ship AI use cases 1 (NL trip parsing) and 2 (route explanations) only. Hard guardrails: LLM output constrained to Pydantic schemas; explanation prompt receives only computed metrics. **Privacy:** NL requests are sent to the LLM without stored user identifiers; precise coordinates are excluded from prompts where the text suffices; server logs redact request text and coordinates beyond a short debugging retention window; third-party processing (Google/Gemini, Mapbox) documented in a privacy page.
10. **API contract.** Platform-neutral display-ready JSON (PRD §19 shape): labels, sort orders, explanation text, warnings computed server-side so clients are thin renderers. **Every user-facing data point carries provenance metadata**: status enum (`live | scheduled | estimated | unknown | user_reported | ai_generated`) plus data version / `last_verified_at` where applicable — the PRD §20 guardrails as schema, not prose. OpenAPI spec → generated TypeScript client for web; same endpoints later consumed by Swift client.
11. **Abuse and cost protection.** **Request validation precedes any paid provider call**: origin/destination must fall inside the region bounding box, radii/candidate counts capped, times within a sane window — out-of-bounds requests are rejected before Mapbox/Gemini/OTP fan-out. All expensive endpoints (trip search, AI parse, geocoding proxy) rate-limited per IP + server-issued anonymous session token; anonymous parking feedback rate-limited, length-capped, and sanitized; Mapbox tokens domain-restricted and all provider keys server-side; spend alerts per provider (belt-and-suspenders with §2 quotas).
12. **Web client.** Next.js + MapLibre GL (MapTiler free tier; self-hosted Protomaps documented fallback). Geocoding/autocomplete via Mapbox Search API behind a `GeocodingProvider` interface. UI ships **7 sorts** (Best Overall, Fastest, Cheapest, Least Driving, Most Driving, Fewest Transfers, Best Parking) + **3 filters** (avoid tolls, avoid city driving, max walk time). **This is an explicit, user-approved amendment of PRD §8.3's 17-mode list for launch**: the remaining modes (lowest gas, least walking, most reliable, lowest emissions, prefer rail/subway, avoid buses) exist in the scoring engine and are candidates for a post-launch "advanced options" drawer. Bike/scooter toggle ships with the GBFS fast-follow, not before its pipeline exists. Route comparison table, route detail with map polylines, NL input box, feedback submission. Deployed behind a real domain with HTTPS.
13. **iOS client (immediately after web).** SwiftUI + native MapKit + Apple geocoding; Apple Maps handoff for driving turn-by-turn. Thin renderer of the same API. App Store submission during September.
14. **No accounts at launch.** Device-local preferences (localStorage / UserDefaults) behind a `PreferenceStore` interface. **Schema-side only**: nullable `user_id` on relevant tables from day one — but the API does **not** accept client-supplied user identifiers pre-auth (spoofing/linkage risk); clients get a **server-issued anonymous session token** used for rate limiting and feedback attribution. When accounts arrive (Sign in with Apple / magic link), authenticated identity populates the existing columns without schema or logic changes.
15. **Verification.** Automated first: **golden-fixture regression trips** (known origin/destination/time → expected itinerary shape) plus edge-case and failure-injection tests — midnight/DST/holiday schedules, no-route cases, provider timeouts/nulls, permit-only parking, alert-flood scenarios. Then human QA: 20–50 real NJ/LI/CT→NYC trips compared against Google/Apple, parking/fare spot-checks, scoring-weight tuning. Milestone-gated, not calendar-gated.

## Key decisions & tradeoffs

- **Web before iOS** (recruiters click links; API hardens before Swift freezes against it) — iOS is still a first-class, immediate follow-up.
- **Python/FastAPI over NestJS**: data-engineering and LLM-validation strengths (Pydantic doubles as the AI guardrail layer) outweigh single-language convenience; web stays typed via generated client.
- **Self-hosted OTP + Mapbox traffic (Option D) over Google-API backend**: flat ~$30/mo vs per-search costs that scale against us; avoids Google display-terms conflict with MapLibre; traffic-aware drive legs are non-negotiable because rush-hour "drive vs park" is the app's central question; strongest portfolio story.
- **Matrix-for-pruning, Directions-for-finalists**: respects Mapbox's 10-coordinate `driving-traffic` Matrix limit and gets geometry/toll data only where it's shown — cheap and correct beats one imaginary bulk call.
- **Rail-first coverage** (all commuter rail + subway + PATH + NJT commuter bus at launch; local buses + GBFS micromobility fast-follow): local bus GTFS triples graph pain while adding little park-and-ride value; no UI promises (bike toggle) ahead of their pipelines.
- **Parking depth is tiered** (top ~60–75 stations deep, everything else honestly "unknown" but still candidate-eligible) because hand-researched parking data is the scarce resource and the moat.
- **Alerts inform scoring and display; they never fabricate ETAs.** ETA math waits for structured TripUpdates (v1.1). Honest labeling per PRD §20.
- **Gemini 2.5 Flash-Lite behind `LLMProvider`**: model choice is deliberately a config detail; provider-agnostic AI layer is itself a design goal.
- **7 sorts + 3 filters in UI; engine classifies all 17 PRD modes as filter/weight/sort-key with tests**: restraint in UI, rigor in engine. "Most Driving" mode (drive ~90%, park destination-adjacent) forces corridor-wide, isochrone-based candidate search rather than an origin-centric radius.
- **No accounts** until cross-device sync earns them; seams pre-cut (nullable user_id, PreferenceStore).

## Risks / open questions

- **OTP graph scale**: full NYC-metro rail graph on a 16 GB box is believed sufficient but unproven until first build; off-box builds (already planned) also derisk serving-box memory pressure.
- **NJ Transit GTFS access**: NJT requires developer-portal registration; terms and feed freshness need verification at Phase 0 (PRD §25 list).
- **Fare/toll-table drift**: effective-dated tables with verification windows and refresh flags mitigate, but a missed hike still shows stale estimates until caught.
- **Parking data accuracy**: even top-75 seed data can be wrong on the ground; user feedback loop and "not guaranteed" disclaimers are the mitigation, not a fix.
- **Mapbox free-tier dependence** for traffic/isochrones/geocoding: fine at portfolio scale; interfaces make paying or swapping providers a contained change.
- **Precomputed station→destination transit times** add a batch job and staleness dimension (refreshed per graph build); acceptable because candidate *selection* tolerates approximation — final itineraries are always live OTP queries.
- **Solo verification bandwidth**: agents outpace the human QA loop; milestone gates + golden fixtures force verification before expansion.

## Launch-scope amendments to the PRD (authoritative)

Where this plan and `multimodal_park_and_ride_prd.md` conflict, **this plan governs for the launch build**; the PRD remains the long-term product vision. Explicit deltas, each user-approved during the grill:

1. **PRD §8.3 (17 sort modes):** launch UI ships 7 sorts + 3 filters (§12); remaining modes live in the scoring engine, surfaced later via an advanced-options drawer. "Most Driving" added as an 18th engine mode.
2. **PRD §8.7 / §9.8 (micromobility):** GBFS/bike/scooter support deferred to the post-launch fast-follow work package (§3); no bike/scooter UI at launch.
3. **PRD §5.1.10 / §15 (region):** launch coverage is rail-first across the full NYC metro (NJT rail + commuter bus, LIRR, MNR, subway, PATH, CT rail); local buses deferred (§3).
4. **PRD §12.4 / §12.5 (AI use cases 3–4):** preference-profile learning and rerouting assistant deferred; launch ships NL parsing + explanations only (§9).
5. **PRD §9.2 (Google as provider):** not used at launch; Mapbox fills driving/geocoding roles behind interfaces.
6. **PRD §7 / §19 fare examples:** all fare figures in the PRD are illustrative; effective-dated fare tables are the only source of truth (§7).

## Out of scope

- Turn-by-turn navigation (handoff to Apple/Google Maps only); payments of any kind; guaranteed/reserved parking; in-app scooter unlock; nationwide coverage; user accounts at launch; ETA adjustment from alerts and delay-aware rerouting at launch (v1.1 with TripUpdates); local buses and GBFS micromobility at launch (fast-follow); preference-learning AI and rerouting assistant AI (deferred); monetization; Android client until after iOS ships.
